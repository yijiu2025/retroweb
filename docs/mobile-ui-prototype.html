RetroWeb 手机端 UI 方案

可交互原型 —— 右边这台 390×844 里可以直接点。配色刻意没照抄参考图：只借它的版式骨架（暖底、深色主卡、大留白、轻描边、圆角大）， 色板仍用 retroweb 的化学蓝。主色是产品识别，改掉等于换品牌。

1导航：侧栏改底部页签

现状：AppShell 在 <768px 只把侧栏收成 64px 图标条 —— 仍占 64px 宽、图标无文字、5 个入口要靠记忆。 手机端改为底部固定 5 格页签（拇指热区），侧栏整个不渲染。 isMobile 目前只参与收侧栏，这次让它参与布局切换。

2标定态：一张卡说清「拆什么、能不能跑」

桌面那张 666 行的居中大卡片在手机上信息过载。改成四段：目标结构（主卡，一眼认得出） → 模型状态条（颜色即语义） → 主操作按钮（50px 高） → 参数速览 4 行。 参数细节不再预展开，点任一行进全屏 sheet。

关键取舍：状态用颜色 + 文案双通道（绿=可用 / 蓝脉动=加载中 / 红=不可用），不只靠文字也不只靠颜色 —— 色弱用户与灰度屏都能读。

3路线态：横向树 → 单列时间轴

逆合成树在桌面是横向拖拽，手机上完全不可用。改成单列时间轴：已完成的步骤收起成一行摘要（步骤名 + 概率 + 结构芯片）， 当前步展开，未来的步折叠。这样一屏能看 5~6 步，而不是横向挤 2 步。

4横竖屏分工：只有 2 个场景要横屏

用户要求「大部分竖屏」—— 实测下来正好也是这个结论，只有两处物理上放不下：
· 结构画板（Ketcher）：左侧笔杆 + 中间画布 + 右侧模板，竖屏必然挤成一条缝。
· 路线网络画布：RouteCanvas 是拖拽 + 滚轮缩放（zoomAt 按 clientWidth 算锚点），且没有任何 touch 事件 —— 手机上双指缩放直接不可用。
这两处点进去时给「请横屏」提示并尝试锁定方向，其余全部竖屏。

5触摸手势要补的（现状缺口）

  • 所有可点元素 ≥44×44 —— 现在 `icon-btn` 34×34、`tab` 约 40px，偏小
  • RouteCanvas：滚轮缩放是非被动监听（preventDefault），手机上要加 双指 pinch 与单指拖拽（现在是直接改 scrollLeft，触摸设备不产生滚动）
  • 横滑列表：询价 / 供应商 / 模型用 scroll-snap 横滑卡，不用竖排（省一屏高度）
  • 底部安全区：页签与 sheet 都要加 env(safe-area-inset-bottom)（iPhone home 条）
  • 键盘弹起：SMILES 输入框聚焦后 sheet 要能被顶上去，不能被键盘盖住

6断点建议

现状全仓只有 1180 / 768 两个断点（TasksView 另有 900），没有 480 一档 —— 小屏 iPhone SE 一到 390 就直接命中 768 那条最粗的规则。 建议补：≤1024 平板降级 / ≤768 手机竖屏（主）/ ≤480 小屏收紧间距与字号 / 横屏且 ≤900 进画板模式。

7不做什么（避免过度设计）

不做移动端专属功能、不做手势返回、不做离线。不改任何业务逻辑与接口 —— 这套纯版式层，靠 matchMedia + CSS 断点分流，现有 store / 组件逻辑原样复用。
